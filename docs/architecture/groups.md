# Groups

Architecture notes for groups. Sections are in build order and keep the version that introduced them; later sections can override earlier ones. A quoted section name may live in another file: see `docs/architecture/README.md`.

## Groups, protocol v22 (v0.37.0, structure part 1 of 3)
- Relay and shared only; no web UI yet (part 2). `PROTOCOL_VERSION = 22`; v21 pages get `version_mismatch` ("please reload"). Stored `SCHEMA_VERSION = 13`.
- A group is a set of items, not a place (frames are places): `groupSchema` `{ id, label, color, members, rev }`. `label` is cleaned like a frame title (`cleanGroupLabel`: one line, controls and invisible characters gone, trimmed, may be empty, at most `MAX_GROUP_LABEL` 40 characters). `color` is a key from `GROUP_COLORS` (= `FRAME_COLORS`: neutral plus the six note hues), never CSS. `members` are note and shape ids only (never frames, connectors or groups: no nesting), distinct, `MIN_GROUP_MEMBERS` 2 to `MAX_GROUP_MEMBERS` 100, in id order. No author, no z, no box: pages derive the box from the members' boxes plus padding, and part 2 draws groups as one fixed layer above frames and below arrows, notes and shapes (not in the shared stacking space).
- An item is in at most one group (`group_members.item_id` is the primary key). Caps: `MAX_GROUPS_PER_ROOM` 30 (`groups_full`); members bounded by the room's note and shape caps (250).
- Client (strict): `groupCreate { clientRef, label, color, members }` (0 to 100 distinct ids pass the schema, so the relay can answer fewer than 2 with `group_size`), `groupUpdate { id, label?, color? }` (at least one), `groupMembers { id, add, remove }` (each 0 to 100 distinct ids, at least one id in all, none in both), `groupDelete { id }` (ungroups: the items stay). Server: `groupsSnapshot { groups }` (strict, creation order, on every join right after `connectorsSnapshot`), `groupCreated { group, clientRef? }` (`clientRef` only to the sender), `groupUpdated { group }` (the whole group, members included, after any change), `groupDeleted { id }` (ungrouped or dissolved). Errors: `groups_full`, `group_size`, `unknown_group`, `unknown_item`; the error ref `groupId` (refused update, members, delete, lock, rate) or `clientRef` (create).
- `BOARD_WRITES`: all four true (a lock refuses a guest's with `board_locked` and the ref; hosts go through). Not host-only. During a silent round all four are refused for everyone, the host too, with `silent_active` (checked in `Room.handle` before the handler, like connectors): a group could name notes others can't see.
- The rule (`worker/src/groups.ts`, pure: `regroup(groups, moves, fresh?)`, `memberIndex`): each move puts an item in a group (or none), taking it out of any other; every group whose members change gets one rev bump (a fresh group keeps rev 1); any group left with fewer than 2 is dissolved. The room and every delete path use it, so the rule is in one place.
- Handlers (`Room.handleGroup`, nothing written or relayed on a refusal): create: `groups_full` first, then `group_size` (fewer than 2), then `unknown_item` for any id that isn't a note or shape on the board (an unknown or deleted id, a frame, a connector, a group, and someone's sealed note word for word as a random id, for everyone, its writer too: `NoteStore.canGroup` is `boxOf`, which hides sealed notes from all). A member in another group moves; the sender gets `groupCreated` with its `clientRef`, everyone else without, then one `groupUpdated` or `groupDeleted` per other group touched, in creation order. A 30-group room refuses a create even if that create would dissolve another group. Update: `unknown_group` for an unknown or deleted group; the label is cleaned; unchanged writes and sends nothing; else rev + 1, `groupUpdated` to everyone. Members: `unknown_group`, then `unknown_item` for a bad add; adding a member it has and removing an item it hasn't change nothing (a no-op sends nothing); past 100 after the change is `group_size`; removing down to 1 dissolves it. The changed group's message goes first, then the other groups touched. Delete: `unknown_group`, else `groupDeleted` to everyone; notes and shapes untouched.
- Last write wins in arrival order; every stored change bumps rev (the shapes and connectors pattern: no client message carries a rev; pages apply by rev).
- Deletes (`NoteStore.delete`, `applyBatch`, `deleteShape`, `applyShapeBatch`, so every note and shape delete path is covered: single, batch, Clear board's batches): deleted items leave their groups (`ungroup`, a `regroup` with moves to none), written in the same transaction as the item delete and the connector detaches. Each returns `DeleteEffects { connectors, groups }`; the room broadcasts the item's delete message, then `connectorUpdated` per freed connector, then `groupUpdated` (shrunk, still 2 or more) or `groupDeleted` (dissolved) per group, in creation order (`broadcastEffects`). The relay has no Clear board message: part 2's Clear board should ungroup first (fewer messages; the relay still dissolves correctly if it doesn't). A frame delete touches no group. Burial (End session, idle expiry) drops both tables.
- Sealed notes: never members. During a round every group message is `silent_active` first (a sealed id gets exactly the reply a random id gets); outside one, a sealed row (never written so by us) is `unknown_item` word for word. `groupsSnapshot`, `groupCreated` and `groupUpdated` are `carriesNoteContent` with `scrubFor` entries that leave out a hidden member, and a group left below 2 whole (a backstop). `groupDeleted` names only the group. Groups load skipping members `boxOf` doesn't know (sealed included). The silent canary (`worker/test/silent.test.ts`) proves no group message to anyone carries a sealed id or place.
- Stored schema 13: `groups (id TEXT PRIMARY KEY, label TEXT NOT NULL DEFAULT '', color TEXT NOT NULL DEFAULT 'neutral', rev INTEGER NOT NULL DEFAULT 1)` and `group_members (item_id TEXT NOT NULL PRIMARY KEY, group_id TEXT NOT NULL DEFAULT '') WITHOUT ROWID` (one row write per member; read in id order). Additive migration 12 -> 13 (`CREATE TABLE IF NOT EXISTS`, no other table touched). `NoteStore`: `allGroups`, `getGroup`, `groupCount`, `groupOf`, `groupMap`, `canGroup`, `saveGroups(next)` (writes only the difference in one transaction: new, changed and gone group rows; one upsert per member that joined or moved, one delete per member that left). Loaded once per wake after notes and shapes: a member that isn't a note (not sealed) or shape here is skipped, and a group row that doesn't validate (a non-key colour, an unclean or long label) or is left with fewer than 2 members is dropped, in memory only (loading writes nothing; its rows stay until written again or burial; a stale member row never blocks an item joining another group, as member writes are upserts). Tested against `worker/test/fixtures/schemaV12.ts` with v0.36.0's exact statements.
- Rollback: a v0.36.0 Worker never reads the tables; while it runs, deleting a note or shape doesn't take it out of its group, and after rolling forward those members are skipped on load and a group left below 2 is dropped (hidden, never an error). See PHASE_PLAN.md "7c Structure".
- Rate: `GROUP_LIMITS` 2 messages a second (burst 60) and 10 member ids a second (burst 250), per socket, never `SOCKET_LIMITS` (rooms.md "Groups: rate buckets, cap and burial"). Costs in docs/LIMITS.md "Groups".
- Web (part 1): only what the version bump forces. The join sends protocol 22; `RoomSession.onMessage` validates the four group messages and returns before `handle` (no view update, no notice, no error); a group message that doesn't validate is "please reload" like any other. The test helpers' fake relay and `joinRoom` send an empty `groupsSnapshot` like the Worker.
- Tests: `shared/test/groups.test.ts` (schemas, caps, label cleaning, sizes), `worker/test/groups.test.ts` (create, update, members, delete, moves and dissolves, refusals, caps, the delete rule on every path with one-transaction checks, moves write nothing, gating, sealed ids, join order and a mid-round join, a full room's snapshot, burial, rate with explicit time budgets, row costs, migration 12 -> 13), the silent canary and `worker/test/sealed.test.ts` samples, `worker/test/host.test.ts` (the lock), `web/test/session.test.ts` "a v22 relay".

### For part 2 (the groups UI)
- Keep a group model by rev like shapes and arrows: `groupsSnapshot` replaces every confirmed group on each join; `groupCreated` swaps a pending group by `clientRef`; `groupUpdated` by rev (equal or older ignored); `groupDeleted` removes. Treat the relay's messages after an item delete as its word (a shrunk group's `groupUpdated`, a dissolved group's `groupDeleted`).
- Membership is exclusive: on `groupCreated` or `groupUpdated`, items listed there are no longer in any other group; the relay also sends the other groups' updates, but apply them in any order.
- Derive the box from the members' live boxes (also during drags, from the page's own positions) plus padding; nothing is sent for a group when its items move. Moving a group as one is a move of its members (`noteBatch` and `shapeBatch`), not a group message.
- Refusals name `clientRef` (create) or `groupId` for rollback: `groups_full`, `group_size`, `unknown_item`, `unknown_group` (also when a group was dissolved meanwhile: roll back calmly), `board_locked`, `silent_active`, `rate_limited`. A no-op change gets no reply: don't wait for one.
- Pace group messages inside `GROUP_LIMITS` (as `connectors/pace.ts` does for arrows), counting member ids too. Clear board: ungroup first, then delete items. Duplicate and undo: add items first, then `groupCreate` with the returned ids.
- Phones, locked boards (guests) and silent rounds (everyone) should turn the group controls off with the reason.
