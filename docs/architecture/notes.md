# Notes: protocol, size, style, inline editing, z-order

Architecture notes, moved out of CLAUDE.md on 7 October 2026 so they load only when needed. Sections are in build order and keep the version that introduced them; later sections can override earlier ones. A quoted section name ("Frame multi-select") may live in another file: see `docs/architecture/README.md`.

## Notes and protocol v3 (slice 2)
- (v3; now v4, see slice 2.7.) Client adds `noteAdd { clientRef, x, y, color, text }`, `noteEdit { id, text }`, `noteMove { id, x, y, final }`, `noteDelete { id }` (strict schemas: extra fields are refused). Server adds `snapshot` (right after `joined`), `noteAdded` (`clientRef` only in the sender's copy), `noteUpdated`, `noteMoved`, `noteDeleted`; `error` may carry `clientRef` or `noteId` so the sender can roll back. v2 pages get `version_mismatch` (v3 pages too, since v4).
- Board constants (`BOARD_WIDTH/HEIGHT`, `MAX_NOTES_PER_ROOM`, `MAX_NOTE_TEXT`, `NOTE_COLORS`; note sizes since 2.7, below) live in `shared/src/protocol.ts`; tokens.css mirrors the sizes (test checks). Server clamps with `clampNotePosition` / `clampNoteRect`; note text is cleaned with `cleanNoteText` (keeps newlines, may be empty).
- Last-write-wins in arrival order; every stored change bumps `rev`. Non-final moves are relayed to the others only, coalesced per note, at the current rev, never stored. Ops on unknown ids are ignored silently.
- Room DO SQLite: `worker/src/noteStore.ts` (`meta.schema_version`, `notes`). Writes only on add/edit/final move/delete, and only when something changed. Schema change = bump `SCHEMA_VERSION` + a migrate step + tests.
- Rate limit: `SOCKET_LIMITS` (30/s, burst 40); 20 violations within 10 s close the socket.
- Web: `web/src/notes/board.ts` is the pure board state (confirmed vs shown, drafts, pending deletes); `RoomSession` drives it and throttles drags (`MOVE_INTERVAL_MS`). A note with a `draft` is the one being edited. Note colours map to `--sy-note-*` tokens in `web/src/notes/colours.ts`.

## Note size, colour and text style, protocol v4 (slice 2.7)
- `PROTOCOL_VERSION = 4`. A note is `{ id, x, y, w, h, text, color, fontSize, bold, italic, textColor, align, rev, authorId }`. Client adds `noteResize { id, x, y, w, h, final }` (position and size together, applied atomically); `noteEdit` is `{ id, text?, color?, fontSize?, bold?, italic?, textColor?, align? }` with at least one field (Zod refine, `NOTE_EDIT_FIELDS`). Server adds `noteResized { id, x, y, w, h, rev, final }`; `noteUpdated` carries the whole note. `noteAdd` carries no size or style (server uses `NOTE_DEFAULTS`). v3 pages get `version_mismatch`.
- Size constants: `NOTE_DEFAULT_W/H` 160, `NOTE_MIN_W/H` 96, `NOTE_MAX_W/H` 480 (tokens `--sy-note-size/-min/-max`, test checks). `clampNoteRect` clamps size first, then position, so the whole note stays on the board; `clampNotePosition(x, y, size)` clamps at a note's own size.
- Style values are keys, never CSS: `NOTE_FONT_SIZES` (s, m, l, xl), `NOTE_TEXT_COLORS` (auto + six inks), `NOTE_ALIGNS` (left, center, right), `bold`/`italic` booleans. The web maps keys to tokens in `web/src/notes/style.ts` (`--sy-note-font-*`, `--sy-note-text-*` in both themes, `auto` = `--sy-note-fg`); `test/noteStyle.test.ts` checks every key has a token and every ink is 4.5:1 on every note colour in both themes. Styles apply to the whole note (per part since 2.7.2). New text-size utilities must be added to `cn`'s tailwind-merge config (`lib/utils.ts`) or they're dropped next to a text colour.
- Persistence: non-final resizes are relayed (coalesced per note, alongside moves) and never stored; a final resize and an edit are stored only when something changed (tests assert row counts).
- Stored schema: `SCHEMA_VERSION = 2` in `worker/src/noteStore.ts`. Migration 1 -> 2 adds `w, h, font_size, bold, italic, text_color, align` with `NOT NULL DEFAULT` = the defaults; it runs only when the stored version is lower, skips columns that already exist (idempotent if interrupted), and is tested against a v1 fixture (`worker/test/fixtures/schemaV1.ts`). Every future column must have a DEFAULT so the previous Worker can still insert/update (rollback safety, tested). Rows off the board at their size are clamped on load, not dropped.
- Web: `board.ts` adds `resizing` (with `dragging`, `isHeld`: remote moves/resizes are confirmed but not shown), `resizeLocal`, `applyResized`, `styleLocal`, `styleChanges`; `RoomSession` adds `startResize`, `resizeNote` (throttled `RESIZE_INTERVAL_MS` 50), `setNoteSize` (Width/Height fields), `styleNote`. Styles or text set before an add is confirmed go out as one `noteEdit` after it is.
- Resize handles: React Flow `NodeResizer` in `NoteNode` (as in Chalkline's ShapeNode): visible only when selected, editable, not under Hand and confirmed; each note node has the board as its `extent`, so handles stop at the edge. Handle look: `.sy-resize-handle` / `.sy-resize-line` in index.css, sizes `--sy-resize-handle`, `--sy-resize-hit-fine` (touch: 44px hit area). Held notes get class `sy-held` (no easing). Alt+Arrow resizes (`notes/size.ts` `keyResize`, `RESIZE_STEP` 10 / 50).
- Properties fields: `notes/StyleFields.tsx` (Colour, Text, Size sections, Chalkline's field patterns), used by `NoteFields` in the panel and the phone editor sheet. All disabled (and dimmed) while disconnected.
- Also in 2.7 (user requests): the top bar is `z-40` so its menu sits above the side panels (`z-30`); chat entries carry `at` (arrival time on this device, `chat/time.ts`); the floating chat resizes from a top-left grip (`chat/chatSize.ts`, `chat/chatStore.ts`, saved under `STORAGE_KEYS.chatPanel`, layout only; limits mirrored in tokens).

## Title alignment, protocol v5 (slice 2.7.1)
- `PROTOCOL_VERSION = 5`. Notes add `titleAlign` (the first line's alignment; `align` is now the body's), also an optional `noteEdit` field. v4 pages get `version_mismatch`.
- Stored schema `SCHEMA_VERSION = 3`: adds `title_align TEXT NOT NULL DEFAULT 'left'`, then `UPDATE notes SET title_align = align` once, so existing titles look unchanged (tested against `worker/test/fixtures/schemaV2.ts`; v4 code inserting without it still works).
- `NoteCard` renders the title and body as separate blocks (`data-note-title`, `data-note-body`) inside one styled text block (`data-note-text`); size, weight, italic and ink apply to both. `StyleFields` has a Title and a Body alignment group (`alignLabel` in `notes/style.ts`).

## Title styling, protocol v6 (slice 2.7.2)
- `PROTOCOL_VERSION = 6`. Notes add `titleFontSize`, `titleBold`, `titleItalic`, `titleTextColor` (same key sets as the body); `fontSize`, `bold`, `italic`, `textColor`, `align` are now the body's. All four are optional `noteEdit` fields (`NOTE_EDIT_FIELDS`; `NOTE_STYLE_FIELDS` = every edit field but text, used by `board.ts`). New notes get `NOTE_DEFAULTS` (title = body defaults). v5 pages get `version_mismatch`.
- Stored schema `SCHEMA_VERSION = 4`: adds `title_font_size`, `title_bold`, `title_italic`, `title_text_color` (`V4_COLUMNS` in `noteStore.ts`, each `NOT NULL DEFAULT`), then copies the body columns into them once. Tested against `worker/test/fixtures/schemaV3.ts`, including the exact v5 insert/update statements on schema 4 (rollback).
- Web: `notes/style.ts` has `NOTE_PARTS`, `PART_FIELDS` (which note field holds each part's style), `partStyle(note, part)` and `partTextClasses(note, part)`; `NoteCard` styles `data-note-title` and `data-note-body` separately (`data-note-text` is just the clipping box). `StyleFields`' `PartTextSection` renders "Title text" and "Body text" sections (Size, Style = Bold/Italic, Align, Text colour; labels like "Bold title", "Title text colour"), one label-left/controls-right row each so nothing wraps at the 232px panel minimum.
- Worst-case snapshot 401,829 bytes at v6 (404,229 since v8); the test fails under 100 KiB headroom (docs/LIMITS.md).

## Inline editing (slice 2.9)
- Web only (no protocol change). From md up, `uiStore.inlineEdit { id, part, n }` marks the note edited in place (`startInlineEdit` selects it; renamed with the note's server id). `RoomBoard.openEditor(id, { fresh, part, touch })` picks in place (mouse, pen, keyboard; the note on screen, `canvas.visible`) or Properties' Title via `requestEdit` (off screen, or a finger tap); phones keep the sheet. Held notes and disconnected boards don't edit.
- `notes/InlineText.tsx`: two plain textareas (`data-inline="title"|"body"`, never contenteditable) with the part's `partTextClasses`, auto-sized, `nodrag nopan nowheel`, placeholders from `INLINE_PLACEHOLDERS` (`PLACEHOLDER_CLASS`, 3:1 tested). Text is the note's draft (`setDraft`), committed once by `commitEdit` (Enter in body, Esc, blur outside), so remote edits never clobber typing and there are no per-keystroke messages. Pure helpers in `notes/inlineEdit.ts`: `inlineKeyAction`, `fitsCap` (280 across title + newline + body; input past it is refused), `titleLine`, `pasteInto` (cleaned plain text, cut at the cap).
- `NoteCard` ignores key and focus events whose target isn't the card (they're the text's); the textareas stop propagation, and the global shortcut guards already skip textareas. While editing the card is `role="group"`, `data-editing`, `nodrag`, with a `ring-focus` ring; double-click picks the part from `data-note-body`.

## Z-order, protocol v8 (slice z-order)
- `PROTOCOL_VERSION = 8`. Notes add `z` (integer, server-assigned only, within ±`NOTE_Z_LIMIT` = 100,000; no client message carries it). Client adds `notesOrder { ids, action }` (strict envelope, 1 to `MAX_BATCH_ENTRIES` ids, `action` in `ORDER_ACTIONS` = front | back); ids are checked one by one by `checkOrder` (bad ones reported by index, the rest applied; a repeated id refuses the whole message with `noteIds`). Server adds `notesOrdered { results: [{ id, z, rev }] }` (up to `MAX_NOTES_PER_ROOM` results) to everyone. v7 pages get `version_mismatch`.
- Stacking helpers are pure and shared (`shared/src/stack.ts`, on `{ id, z }` only so later objects can reuse them): `compareStack` (z, then id in code-unit order), `stackOrder`, `restack` (front/back keeping relative order; only notes that must move change, a moved note never ties; past the bound the whole room is renumbered 0..n-1), `zForNew` (max + 1, renumbering first at the bound), `clampZ`.
- Worker (`room.ts` `handleOrder`): computes from the room's current stack, so the later of two arrives on top. Changed notes get one rev bump each, written in one `applyBatch` transaction; results list every named note (changed or not, so the sender reconciles) plus any renumbered note, in one broadcast. Unknown/deleted ids ignored; only-unknown sends nothing. `noteAdd` puts the note at `zForNew` (a renumbering at the bound is broadcast as `notesOrdered` before `noteAdded`). A notesOrder is one message for `SOCKET_LIMITS` and its ids spend `BATCH_LIMITS`.
- Stored schema `SCHEMA_VERSION = 5`: `z INTEGER NOT NULL DEFAULT 0`, then once `z` = each note's rank by rowid (0..n-1: how notes were stacked before). Tested against `worker/test/fixtures/schemaV4.ts`, including the exact v7 insert/update statements on schema 5 (a note v7 code inserts gets z 0). Out-of-bound z is clamped on load. The snapshot stays in creation order; stacking is by z.
- Web: `board.ts` `reorderLocal` (optimistic, shared `restack` on what's shown; no optimistic change when the server would renumber) and `applyOrdered` (confirms z/rev, changes only z on the shown note, same entries when unchanged); `addLocal` puts the note on top. `RoomSession.orderNotes(ids, action)` leaves out unconfirmed notes and sends chunks of 50 in stacking order (front bottom-up, back top-down) so relative order survives; refused `noteIds` roll back. `notesOrdered` is one view update.
- React Flow: node `zIndex` = `note.z`; `FLOW_STACKING` (`elevateNodesOnSelect: false`, `zIndexMode: "manual"`) is spread on `<ReactFlow>`; held and selected notes are no longer raised; the board node sits at `-NOTE_Z_LIMIT - 1`. DOM (and so Tab) order and the minimap stay in creation order on purpose: reordering DOM nodes would blur a note being edited in place when someone else restacks.
- UI: `notes/OrderFields.tsx` (`ORDER_COMMANDS`, `OrderSection` with labelled Bring to front / Send to back buttons) in Properties (one note via `NoteFields`, several via `SelectionFields`), the phone editor sheet, and an "Order" group in `SelectionBar`. Disabled while disconnected or before a note is confirmed. No keyboard shortcut (Chalkline has none; it uses layers).

## Silent brainstorm: sealed notes and the leak inventory, protocol v17 (v0.25.0, part 1)
- The round, the messages and the rules are in facilitation.md "Silent brainstorm, protocol v17". This section is what a note looks like while sealed and every path that could send one.
- Stored schema `SCHEMA_VERSION = 10`: notes gain `sealed INTEGER NOT NULL DEFAULT 0` and `writer TEXT DEFAULT NULL` (migration 9 -> 10 skips columns that exist; tested against `worker/test/fixtures/schemaV9.ts`, including v0.24.0's exact note and frame statements on schema 10: its notes are never sealed). A note on the wire never has either field (`noteSchema` strips unknown keys). `NoteStore` keeps sealed notes' writers beside the note cache (`writerOf`, `sealedCount`, `sealedBy`, `hasSealed`); `insert(note, writer)` and `applyAdds(..., writer)` seal; `reveal(meta)` sets `sealed = 0, writer = NULL` on every sealed row and writes the meta keys in one transaction (1 row per note plus the flag); a sealed note deleted keeps its writer in `goneWriters` until the next message (`forgetGone`), so its `noteDeleted` is still filtered. A sealed row without a writer (never written by us) gets "" and is visible to nobody until a reveal. Rollback: v0.24.0 code doesn't know `sealed` and would show sealed notes to everyone (reveal or end a round first).
- One filter for everything: `SERVER_MESSAGES` (shared) marks every server message type `carriesNoteContent` (a `Record`, so a new type needs a decision; a test compares it with the schema's variants). `Room.send` and `Room.broadcast` pass every marked message through `scrubFor(message, visible)` (`worker/src/sealed.ts`, one entry per marked type, compiler-checked) with the recipient's writer id from its attachment; `visible(id)` = the note isn't sealed, or its writer is the recipient's. Broadcasts encode once per distinct writer; with no sealed note the filter is skipped. The handlers also treat someone else's sealed note as unknown (`Room.noteFor`), so the filter is the backstop, not the only check.
- Leak inventory (every server message that can carry a note, from a grep of `worker/src/room.ts`; who may receive it while a round is silent):

| Server message | Carries | Sent from | While silent, who gets a sealed note in it |
|---|---|---|---|
| `snapshot` | every note, whole | `join` (first join, reconnect, second tab, after a wake) | each socket: unsealed notes plus its own writer's sealed notes |
| `noteAdded` | whole note (+ `clientRef` to the sender) | `noteAdd` | the sender (with `clientRef`) and its writer's other sockets; everyone else only `silentChanged` |
| `noteUpdated` | whole note | `noteEdit` | the writer's sockets |
| `noteMoved` / `noteResized` | id, place, size, rev | `noteMove` / `noteResize`, live (coalesced in `flushMoves`) and final | the writer's sockets (live: its other sockets) |
| `noteDeleted` | id | `noteDelete` | the writer's sockets; everyone gets the new count |
| `notesBatchApplied` | id, place, size per entry | `noteBatch` live and final | results filtered per recipient; nothing when none is left; a count if a sealed note was deleted |
| `notesOrdered` | id, z, rev | `notesOrder`; renumbering at the bound in `noteAdd`, `shapeAdd`, `itemsAdd` (`newOnTop`, `handleItems`) | results filtered per recipient (sealed notes are still renumbered and written) |
| `frameMoved` | carried notes' id, place, rev | `frameMove` (live and final) | none: frameMove is refused while silent; the filter drops hidden carried notes anyway |
| `itemsAdded` | notes with content (+ refs and refusals to the sender) | `itemsAdd` (duplicate, undo, templates) | the sender in full; others' copies without hidden notes (frames and shapes stay), nothing when empty |
| `voterGranted` | note ids of my votes | `claimVoter` | filtered; votes are never on sealed notes |
| `voteConfirmed` | note id | `voteSet` | never: a vote on a sealed note is ignored (anyone's, its writer's too) |
| `votesRevealed` | note ids with totals | `voteStop`, `join` while closed | filtered; never names a sealed note |
| `notesRevealed` | whole notes | `silentReveal` | everyone (the notes are unsealed first) |
| `error` | `noteId`, `noteIds`, `clientRef` echoed | refusals, rate limits, lock | the sender only, echoing ids it sent itself: the same reply as for an unknown id |
| `silentChanged` | `active`, `count` | start, reveal, each sealed add or delete | everyone: one number, never whose |
| `joined` | `silent { active, count }` | `join` | the joiner |

- Everything else (`welcome`, `participant_*`, `echo`, frame and shape messages, host, lock, timer, voting state, cursors) carries no note content. Error texts are fixed strings: none echoes note text, a sealed id it wasn't sent, or a writer id; `worker/src` still has no `console.`.
- What a non-writer can still infer: the count (by design), and that sealed notes take part in stacking (z is one space, so a visible note's new z lands above them). Never content, id, place, size, colour or author.
- Tests: `worker/test/silent.test.ts` (the canary test reads every raw message to the host, a passive guest, a late joiner and the guest's second tab while one guest drives every note message, a second tab, a reconnect and an eviction; probes compare the reply to someone else's sealed id with the reply to a random unknown id, byte for byte), `worker/test/sealed.test.ts` (one sample per marked type), `shared/test/silent.test.ts` (registry, schemas, sizes).
