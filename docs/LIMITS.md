## Flags: numbers that could threaten the plan

1. **Live cursors vs DO requests.** At about 20 cursor messages per second per user and 20:1 billing, one active user costs about 1 request/s (3,600 per hour). Ten people moving cursors for an hour is about 36,000 of the 100,000 daily DO requests. A few workshops a day fit, but cursors are the biggest consumer by far. Consider sending cursors only while moving, lower rates on phones, and coalescing.
2. **SQLite rows written (100k/day).** If every drag batch or keystroke is persisted, a busy session could use thousands of writes. Persist on drop / debounce, not per movement message (slice 2/5 decision).
3. **Duration (~29 object-hours/day awake).** A room with steady cursor traffic never hibernates. Fine for a few rooms a day, tight if rooms are left open with an active tab sending heartbeats. Avoid app-level heartbeats (pings get auto-pongs without waking the object) and let idle rooms hibernate.
4. **Daily hard stop.** When any allowance runs out, operations fail until 00:00 UTC. That's acceptable for a hobby project, but slice 4 (reconnect) should show a clear "relay is over its daily limit" state rather than reconnecting in a loop, which would make it worse.
5. **Worker CPU 10 ms per request.** Fine for routing, Origin checks and HMAC verification of room codes (slice 1). Keep heavy work in the Durable Object, which gets 30 s.

Nothing else looks close: storage, connection count and message size are far above what this app needs.

## Slice 1: what rooms and the limiter cost

Estimates against the free allowances above (checked 2 October 2026).

**Limiter Durable Object (room creation).** Every `POST /rooms` that passes the Origin, config, kill-switch and body checks makes one RPC call to the single `Limiter` object: **1 DO request**. It reads a few rows (lockout, failure counts, today's creations) on every call, but **writes only when a counter changes**: a failed passcode (1 insert, plus 1 lockout row on the 5th), or a granted creation (1 upsert). Old rows are pruned in the same calls. Refused attempts (locked out, over a cap) write nothing. Worst case per day is bounded by the caps: about 50 creations and roughly 50 failures an hour, so well under 2,000 row writes/day even under steady guessing.

**Room codes.** Verified in the Worker with one HMAC before any Durable Object is addressed, so invented or tampered codes cost one Worker request and **zero** DO requests. `GET /rooms/check` (used only after a socket fails to open) is the same.

**Echo traffic.** A room stores nothing (no rows read or written). Each socket opening is 1 Worker request + 1 DO request. Inbound WebSocket messages bill at 20:1, so 100 `say` messages ≈ 5 DO requests; the fan-out to other sockets is outgoing and not billed as requests. The per-socket token bucket (5/s, burst 10) caps one socket at about 0.25 DO requests/s (≈ 900/hour). Per-socket state lives in the WebSocket attachment, so idle rooms hibernate and use no duration.

**Residual risk.** None of this stops a script from spending the **daily request budget** (100,000 Worker requests, 100,000 DO requests): Origin checks don't apply to scripts, invalid codes are cheap but still count as Worker requests, and a valid room link can be used to open many sockets. If that happens, the free plan **fails closed**: requests error until 00:00 UTC, then everything recovers. No bill, no data at risk; the app is simply unavailable for the rest of the day.

## Slice 2: what notes cost

Estimates against the free allowances above (checked 2 October 2026; not re-checked for slice 2).

**Writes (100,000 rows/day).** Only commits write: an add, an edit that changes the text, colour or style, a drop that changes the position, a resize release that changes the size, a delete. Each is **1 row**. Dragging and resizing in progress write nothing (tested). A busy workshop (20 people, 50 notes each edited and moved a few times) is a few thousand row writes. Plus 1 row when a room's tables are first created.

**Reads (5,000,000 rows/day).** Notes are read once when the Durable Object wakes (up to 200 rows, plus 1 for the schema version) and then served from memory. A room that hibernates and wakes often re-reads them each time.

**Requests.** A drag or a resize sends about 20 messages a second (20:1 billing → about 1 DO request/s per person dragging). The per-socket bucket is now 30/s with a burst of 40 (it was 5/s), so a script on one socket can spend up to about 1.5 DO requests/s. Twenty violations within 10 seconds close the socket.

**Batches (protocol v7, slice 2.8).** A group move, arrange or group delete goes out as `noteBatch` messages of up to `MAX_BATCH_ENTRIES` = 50 entries.
- *Writes:* a final batch of N changed notes is **N row writes** (one per moved, resized or deleted note; unchanged entries write nothing) in one SQLite transaction. Arranging all 200 notes is 200 rows (4 batches); dragging a 50-note selection and dropping it is 50 rows. A busy workshop that arranges often might add a few thousand rows a day, still well inside 100,000. A live group drag (`final: false`) writes nothing (tested).
- *Requests:* a batch is **one message** (one token from the 30/s bucket, and 1/20 of a DO request), whatever its size. The web sends a live group drag at most every 100 ms (`GROUP_MOVE_INTERVAL_MS`), so dragging a group costs about 10 messages a second, half a single-note drag.
- *Entries budget:* entries also spend a separate per-socket bucket, `BATCH_LIMITS` in `worker/src/limits.ts`: **600 entries a second, burst 1,000**. A 50-note live drag needs 500 a second; a 200-note arrange needs 200 at once. A batch over budget is dropped with `rate_limited` naming its notes (the sender rolls them back) and counts as a violation, exactly like the message bucket (20 in 10 s close the socket). Relaying is the main cost here: one live 50-entry batch fans out as a message of about 3.5 KB to each other participant.
- *Message cap:* `MAX_MESSAGE_BYTES` stays at **4 KiB**. The largest valid batch (50 resize entries with 4-digit positions and maximum sizes) is under it (`shared/test/batch.test.ts` checks), so no raise was needed. A `notesBatchApplied` of 50 results is about 5 KB, far under the 512 KiB server message cap.
- *Snapshot:* unchanged by v7 (401,829 bytes worst case; v8 adds z, see below).

**Stacking order (protocol v8, slice z-order).** Bring to front and Send to back go out as `notesOrder` messages of up to 50 note ids.
- *Writes:* only notes whose z actually changes are written, **1 row each**, in one SQLite transaction. Bringing one note to the front is 1 row; pressing it again on a note already on top is **0 rows** (tested), as is any action that leaves the order as it was. Bringing 50 notes to the front is at most 50 rows (fewer where some already sit above the rest in the right order).
- *Renumbering:* z is kept within ±100,000 (`NOTE_Z_LIMIT`). An action (or a new note) that would pass it renumbers the whole room 0..n-1 in the same transaction: up to **200 rows** once. Reaching the bound takes about 100,000 Front (or Back) presses in one room, so this is rare; at the 30/s message bucket a script needs nearly an hour of steady sending to force one, and then another 100,000 to force the next.
- *Requests:* a `notesOrder` is **one message** (one token from the 30/s bucket, 1/20 of a DO request), whatever its size, and its ids spend the same per-socket entries bucket as batches (`BATCH_LIMITS`, 600 a second, burst 1,000). Over budget: dropped with `rate_limited` naming its notes (the sender rolls them back), counted as a violation. A 200-note selection is sent as 4 messages (chunks of 50 in stacking order) and spends 200 entries.
- *Fan-out:* one `notesOrdered` to everyone, with every named note (changed or not) and any note a renumbering moved: about 60 bytes per note, at most 200 notes (about 12 KB), far under the 512 KiB server cap.
- *Message cap:* the largest `notesOrder` (50 ids) is about 1 KB, under `MAX_MESSAGE_BYTES` = 4 KiB (`shared/test/zOrder.test.ts` checks).

**Storage.** At most 30 frames × about 0.3 KB, and at most 200 notes × about 1.3 KB (slice 2.7 adds seven small columns, size and style keys; 2.7.1 one more, the title's alignment; schema 5 one integer, z) = well under 1 MB per room. Since v0.14.0 idle rooms expire (below), so storage no longer grows without bound.

**Messages out.** The web accepts server messages up to `MAX_SERVER_MESSAGE_BYTES` (512 KiB). Outgoing messages aren't billed as requests.

**Frames (protocol v9, slice frames).** Up to `MAX_FRAMES_PER_ROOM` = 30 frames per room, in their own `frames` table (schema 6).
- *Join and reconnect: two messages.* The notes `snapshot` keeps its shape and its worst case (404,229 bytes, below). Frames follow in their own `framesSnapshot`, sent in the same handler step so nothing lands between them. Worst case for the frames message: **15,096 bytes (14.7 KiB)**: 30 frames at the largest size, 60-character titles of lone surrogates (6 bytes each when escaped), the longest colour key and `rev` at `Number.MAX_SAFE_INTEGER` (protocol v9). The notes snapshot's 400 KiB tripwire and 100 KiB headroom rule are unchanged and apply to that message on its own.
- *Frame title style (protocol v10, schema 7):* five keys per frame (`titleFontSize`, `titleBold`, `titleItalic`, `titleTextColor`, `titleAlign`) add 107 bytes per frame at their longest values, so the frames message's worst case is now **18,306 bytes (17.9 KiB)**. That was over the old 16 KiB test cap, so the cap was raised to **20 KiB** (decided 4 October 2026, `shared/test/frameTitleStyle.test.ts`). Why that's fine: it's a separate message from the notes snapshot, about 3.6% of the 512 KiB server cap, and the notes snapshot's tripwire and headroom rule don't change. Rule: a new per-frame field that takes the worst case within 10% of the cap needs a decision first (the test fails above 18,432 bytes, 90% of the cap, so almost any new per-frame field trips it). Storage: five small columns per frame, under 50 bytes a row.
- *Combined reconnect payload:* **422,535 bytes (412.6 KiB)** per person on a full board with a full set of frames (404,229 + 18,306; v9 was 419,325), in two messages, each under the 512 KiB cap.
- *Reconnect storm (slice 4):* 20 people on a full board rejoining at once is now about **8.45 MB** of outgoing messages (20 × 422,535), up from about 8.39 MB in v9 (20 × 419,325) and about 8.1 MB for notes alone (20 × 404,229). Outgoing messages aren't billed as requests; this is bandwidth and CPU in one wake, not budget.
- *Writes:* adding a frame is **2 rows written** (the row and its primary-key index entry; SQLite counts both, and the same is true of adding a note). A title, colour or title style edit that changes something (any mix of fields in one message), a final resize that changes the size, and a final move of the frame alone are **1 row** each; unchanged ones write nothing. A final move that carries N notes is **1 + N rows** at most (only rows that changed), in one transaction. Live moves and resizes write nothing (tested). Deleting a frame is 1 row (plus its index entry) and never touches notes.
- *Requests:* frame messages are ordinary messages under `SOCKET_LIMITS` (30 a second, burst 40). The web throttles live frame moves and resizes like notes (`MOVE_INTERVAL_MS` / `RESIZE_INTERVAL_MS`, about 20 a second).
- *Entries budget:* the note ids a **final** `frameMove` carries (up to 50) spend `BATCH_LIMITS` entries (600 a second, burst 1,000), like a batch; over budget is `rate_limited` naming the frame and its notes (the sender rolls both back) plus a violation. Live moves carry ids too (so others see the notes follow) but don't spend entries; they're throttled and never stored.
- *Message caps:* the largest `frameMove` (50 carried ids, 4-digit position) is about 1 KB, well under `MAX_MESSAGE_BYTES` = 4 KiB, so the carry cap stays at 50. The largest `frameMoved` (50 carried notes, revs at their maximum) is 3,459 bytes.

**Snapshot size (protocol v8, slice z-order).** Worst case for a full board of 200 notes: **404,229 bytes (394.8 KiB)**, about 2.0 KB per note, leaving **117.2 KiB** (120,059 bytes) under the 512 KiB cap, still above the 100 KiB margin we want. z adds 12 bytes per note at its widest (`"z":-100000,`), 2,400 bytes per full snapshot. It is now only **5.2 KiB (5,371 bytes) under the 400 KiB tripwire** in `shared/test/noteSize.test.ts`: the next per-note field of any size will breach it, so that tripwire (or the note shape, for example shorter keys or a lower `rev` ceiling) must be revisited before adding one. The test also fails if the headroom drops below 100 KiB. (Protocol v6, slice 2.7.2: 401,829 bytes. Protocol v5, slice 2.7.1: 384,829 bytes; v6's four title style fields add 85 bytes per note at their longest values, 17,000 bytes per full snapshot. v4: 380,429; v3: 360,829.) The worst note has 280 lone surrogate characters in its text (JSON escapes each as 6 bytes, `\uXXXX`; 4-byte emoji give less), the longest keys, 4-digit positions, maximum size and `rev` at `Number.MAX_SAFE_INTEGER`. This figure is the notes snapshot alone; since protocol v9 frames come in a separate message (below).

**Create with content (protocol v11, slice create with content).** `itemsAdd` adds notes and frames with their full content (size, text, colour, every style field) in one message. Template apply used it first; since v0.12.0 Duplicate and undo restores use it too (below).
- *Writes:* each added note is **2 rows** (the row and its primary-key index entry) and each added frame **2 rows**, the same as `noteAdd` and `frameAdd` (tested: 3 notes + 2 frames = 10 rows). All of one message's inserts go in **one SQLite transaction**. If new notes would pass the z bound, the room's existing notes are renumbered in that same transaction (up to 200 extra rows, 1 each, as for `noteAdd`; as rare as before). Refused items and a message where nothing is added write nothing.
- *Requests:* an `itemsAdd` is **one message** (one token from the 30/s bucket, 1/20 of a DO request), whatever it carries (tested: 30 messages of 2 notes go through, 60 items being more than the burst of 40). The web sends at most 10 a second (`ITEMS_STEP_MS` = 100 ms, a third of the bucket), so typing or dragging alongside still fits.
- *Entries budget:* each note and frame spends **one entry** from `BATCH_LIMITS` (600 a second, burst 1,000), like batch entries. Over budget: the message is dropped with `rate_limited` naming its `clientRef` (the sender rolls back all its items) and counts as a violation. At the web's pace it spends a few hundred a second at most (10 messages of about 20 items with the shortest content), inside the 600.
- *Message cap: decided to keep `MAX_MESSAGE_BYTES` at 4 KiB* (4 October 2026). The web packs items into messages by their actual serialised size (`packItems` in `web/src/rooms/items.ts`, tested never to exceed the cap and to keep order); every single valid item fits in a message on its own. Items per message (`shared/test/itemsAdd.test.ts`): **2** notes at their largest (280 lone-surrogate characters, 6 bytes each escaped), **6** frames with the longest titles, **15** notes or **21** frames with short content (empty text, 12-character refs as the web sends). So the 50-item envelope limit only matters for a raised cap; in practice the byte cap decides. Today's templates are one message each: the largest (Migration strategy, 6 frames, since v0.29.0) is 1,355 bytes at the board's far corner, about 33% of the cap (tested in `web/test/templates.test.ts`). A template needs one free frame slot per frame of the 30 a room.
- *Fan-out:* one `itemsAdded` to everyone (refs and refusals only in the sender's copy). From a message that fits 4 KiB it is about **4 to 6 KB** (2 maximum notes: 4,183 bytes; 15 short notes: 5,633; 21 short frames: 5,963; 6 maximum frames: 3,923, with ids, revs at `Number.MAX_SAFE_INTEGER` and authors added). The largest the schema allows at all (50 maximum notes, 32-character refs, revs at the maximum) is **103,653 bytes (101.2 KiB)**, about 20% of the 512 KiB server cap (tested). A renumbering at the bound adds one `notesOrdered` (at most 12 KB) before it.
- *Snapshots:* unchanged. The notes snapshot (404,229 bytes) and the frames snapshot (18,306 bytes) and their tripwires are not touched by v11: items are stored as ordinary notes and frames.

**Bar, Duplicate, Undo and Clear board (v0.12.0, web only).** No protocol or storage change; these reuse existing messages, so the costs are the ones above.
- *Duplicate* is an `itemsAdd` (2 rows per copy, one message per packed batch, paced at 10 a second, one `BATCH_LIMITS` entry per copy). It is refused up front, sending nothing, when the board hasn't room for every copy.
- *Undo of a delete or a clear* adds the items back with `itemsAdd`, at the same cost and pace as Duplicate (new ids, new rows). Undo of a move, resize or edit sends the same final `noteBatch`, `noteEdit`, `frameMove`, `frameResize` or `frameEdit` as the original change (1 row per changed item; unchanged ones write nothing). Undo of an add is a batch delete (notes) or a `frameDelete` (frames). The history itself lives only in the page's memory: nothing is stored or sent for it.
- *Clear board* is the notes as final `noteBatch` deletes (4 messages of 50 for a full board, 200 entries, inside the burst of 1,000) and then one `frameDelete` per frame, sent every 50 ms (`CLEAR_FRAME_STEP_MS`, 20 a second): with the four batches, at most 24 messages in the first second, under `SOCKET_LIMITS` (30 a second, burst 40). Writes: 1 row (plus its index entry) per deleted note or frame, as for Delete.
- *Restoring a full board in one undo:* at the 4 KiB cap and with every note at its largest (2 per message) and every frame title at its longest (6 per message), 200 notes and 30 frames pack into **105 `itemsAdd` messages**, about **10.5 seconds** at 10 a second (`packItems`, measured). With short content (15 notes or 21 frames a message) it is about 16 messages, 1.6 seconds. Writes: 460 rows (2 per item), in one transaction per message.

**Reconnect and presence (v0.13.0, web only).** No protocol or storage change; presence uses the existing `joined`, `participant_joined` and `participant_left` messages and costs nothing extra.
- *One reconnect* is what a join costs: **1 Worker request + 1 Durable Object request** to open the socket, two small inbound messages (`hello`, `join`: 1/10 of a DO request at 20:1), and the two snapshots out: **422,535 bytes (412.6 KiB)** combined worst case on a full board with a full set of frames (404,229 + 18,306, as above). No rows are written; the room is read from memory, or from storage (a few hundred rows at most) if the object had hibernated.
- *Retry schedule and cap* (`web/src/connection/reconnect.ts`): after a drop the page tries after about 1, 2, 4, 8, 16, 30, 30 and 30 seconds (±20% jitter, so a room's pages spread out), **at most 8 tries per drop (about 2 minutes)**, then stops and offers Rejoin. Worst case per drop: 8 Worker requests and 8 DO requests (a try that never reaches the relay costs neither). From the fifth socket in a row that never opened (`PROBE_AFTER_FAILED_OPENS` = 5 since v0.15.0; it was 3, which sent a relay restart or deploy of about 10 s into the slow limit state), each failure adds one `GET /health` and one `GET /rooms/check` (Worker only, no DO): at most 4 of each per drop. Tries started by the browser (`online`, the tab visible again) are at least 1 s apart, and `online` starts a new sequence of at most 8. A tab hidden for more than a minute stops trying until it's visible.
- *When the relay looks down* (5 failed opens, about 30 seconds, and a failing health probe): no more sockets; **one `GET /health` a minute while the tab is visible, for at most an hour** (60 Worker requests, 0 DO requests), then Offline. So a stuck or forgotten tab costs at most about 80 Worker requests and 8 DO requests per drop before it stops for good (until someone presses Rejoin or the network comes back).
- *Reconnect storm*: 20 people on a full board rejoining at once (a relay restart or deploy) is about **8.45 MB** of outgoing messages (20 × 422,535, as recorded above), 20 Worker requests and 20 DO requests, spread over a second or so by the jitter. Outgoing messages aren't billed as requests.
- *What a browser can see when the free plan's daily limit is hit* (from Cloudflare's documentation; not tested against the real limit): over the **Workers** request limit, Cloudflare answers with its own error page (error 1027) instead of running the Worker. That page has none of the relay's CORS headers, so `fetch` from the app fails exactly like an unreachable relay, and the WebSocket upgrade fails with no reason given (close code 1006). Over a **Durable Objects** limit, the Worker still runs (so `/health` works), but opening the room fails, and the browser again sees only a socket that never opened. A browser therefore can't tell "over the limit" from "unreachable", or a DO limit from any other failure to open a room. The page claims no more than that: it says the relay "may be unreachable or over its daily limit" only when `/health` also fails, and otherwise just backs off and ends at Offline.

**Idle room expiry (v0.14.0).** No protocol or stored-schema change. Constants in `worker/src/limits.ts`: `ROOM_IDLE_EXPIRY_MS` = 7 days, `ALARM_RESET_SLACK_MS` = 1 hour. (Cloudflare's alarm docs could not be re-checked from the build environment on 4 October 2026: the network blocked developers.cloudflare.com. The figures below are the ones the project owner checked that day.)
- *Alarm cost:* setting the alarm (`setAlarm`) is billed as **1 row written**; reading it (`getAlarm`) is a read. Each alarm firing is **1 DO request**. The alarm is set only when the **last** socket of a room closes, and only when there is no alarm yet or the existing one is more than 1 hour earlier than the new time (the slack rule), so a room costs **at most about 1 row written per hour** for its alarm, however often people come and go. Joining never touches it (tested: 0 rows).
- *Expiry cost:* when the alarm fires with nobody connected, `deleteAll()` empties the room (how Cloudflare bills the rows it removes, at most a few hundred, wasn't checked; it happens once per room) and **one tombstone row** is written (`meta.expired_at`; counted as 2 rows, the row and its index entry). Since v0.15.0 the burial is transactional and writes 5 rows (see Host, lock, timer and End session below). With anyone connected the firing writes nothing.
- *Worst case, a script with a valid room link opening and closing sockets:* each socket costs what it always did (1 Worker request + 1 DO request; Origin doesn't stop scripts). Alarm writes are bounded by the slack rule at about **24 rows a day per room** (one per hour), and **1 DO request a week per room** for the firing. Room links come only from room creation, which is capped (`CREATE_LIMITS`: 50 a day), so the alarm can't be used to multiply writes across invented rooms (invalid codes never reach a Durable Object). A socket held open keeps a room alive; that is "someone is in it".
- *Tombstones:* one small row (a key and an integer) stays per expired room, forever: tens of bytes. An expired room's link opens a socket (1 Worker + 1 DO request), reads the tombstone (1 row) and is closed with 4410; nothing is written (tested).
- *Storage:* a room's notes and frames (well under 1 MB) now go 7 days after its last visit, so storage is bounded by the rooms used in the last week plus one tombstone per expired room. Rooms created before v0.14.0 get their alarm at their next last-close; ones nobody opens again keep their data until then.

**Host, lock, timer and End session (protocol v12).** No stored-schema version change: lock and timer are new meta keys (`locked`, `timer_started_at`, `timer_duration_ms`), like the tombstones. Row counts measured in the worker tests (`rowsWritten`; an insert counts its primary-key index entry too).
- *Host token:* stateless (an HMAC of the room id, derived on demand), so it costs **no storage**. `claimHost` is one message (one `SOCKET_LIMITS` token) and one HMAC in the Durable Object; host status lives in the socket attachment, so it writes nothing. A wrong token is refused with `bad_host_token` **and counts as a violation** (20 in 10 seconds close the socket), so guessing is slow as well as hopeless (256-bit HMAC).
- *Lock:* `lockSet` writes only when the lock changes: **2 rows** the first time (new meta row + index), **1 row** after that. Setting the same value again writes nothing and is answered only to the sender. `lockChanged` goes to everyone (a few dozen bytes).
- *A locked board refuses writes cheaply:* a non-host's board-changing message is answered with `board_locked` before any handler runs: **no rows read or written, nothing relayed**. It still spends the sender's rate budget (one token, and its entries for a batch), so a locked board can't be used to send faster.
- *Timer:* `timerStart` writes both keys in one transaction: **4 rows** the first time, **2 rows** when replacing a running timer. `timerStop` is **2 rows** (deleting both), and nothing when no timer runs. `timerChanged` goes to everyone. A finished timer needs no server action (pages count down from `startedAt` + `durationMs` with the offset from `serverNow`).
- *Joining:* `joined` now carries `locked` and `timer`, read from memory: no extra rows read or written. Worst case `joined` (20 participants with the longest names, all hosts, a timer at its widest) stays under the **8 KiB** tripwire in `shared/test/host.test.ts`. The notes snapshot and frames snapshot are unchanged.
- *End session:* one message from a host. The room is buried like an expired room (`worker/src/expiry.ts`): in **one SQLite transaction** every table but meta is dropped, meta is emptied and the `ended_at` tombstone written; then `deleteAll()` (which also removes the alarm), then the tombstone again. Measured: **6 rows** written (meta rows deleted plus the tombstone twice); dropping tables is not counted as row writes. Everyone gets `sessionEnded` and every socket is closed with 4411. Later visits cost 1 Worker + 1 DO request and 1 row read each, write nothing, and are closed with 4411 at once.
- *Expiry (since v0.15.0):* uses the same burial path, so it writes **5 rows** (the schema-version row deleted, the tombstone twice) instead of 2; still once per room.

**Dot voting (protocol v13).** Relay and plumbing only (no voting UI yet). Stored schema version 8: one new `votes` table (`voter_id`, `note_id`, `count`; primary key voter + note; every column with a DEFAULT), and the voting state as meta keys (`voting_state`, `voting_budget`, `voting_round`). Row counts measured in `worker/test/voting.test.ts` (`rowsWritten`).
- *Voter identity:* stateless. `claimVoter` is one message (one `SOCKET_LIMITS` token) and one HMAC; the voter id (an HMAC of room id and the client's random key) lives in the socket attachment, so a claim **writes nothing**. The raw key is never stored or logged.
- *voteSet:* an ordinary message (one `SOCKET_LIMITS` token, no entries budget). A first vote on a note writes **2 rows** (row + primary-key index), a changed count **1 row**, taking the dots off (count 0) **1 row** (a delete), and the same count again **0 rows** (still confirmed). Refused ones (`voting_closed`, `no_voter`, `over_budget`, `voters_full`) and unknown notes write nothing. `voteConfirmed` (about 80 bytes) goes only to the voter's own sockets; nothing goes to anyone else while voting is open.
- *voteStart:* deletes the previous round's votes and writes the changed meta keys in one transaction: **1 row per deleted vote**, plus 2 rows for a meta key stored the first time and 1 for a changed one (the first round in a room: 4 rows, `voting_state` and `voting_round`, more if the budget isn't the default 5; a later round with the same budget: 1 row for the round plus the deleted votes). Worst case **800 deleted rows** (see below) + 3. `votingChanged` (about 80 bytes) to everyone.
- *voteStop:* **1 row** (`voting_state`), then `votingChanged` and `votesRevealed` to everyone. Stopping when not open writes nothing and answers only the sender.
- *voteClear:* 1 row per deleted vote + 1 row (`voting_state`); nothing when already off with no votes.
- *Deleting notes:* each note delete (single, batch, Clear board) also runs `DELETE FROM votes WHERE note_id = ?` in the same transaction: **+1 row per vote on that note** (0 when it had none; existing note-delete counts unchanged), and a scan of at most 800 vote rows (reads). Nothing is broadcast about it.
- *Worst-case votes rows:* at most `MAX_VOTERS_PER_ROUND` (40) voters a round (with votes this round or claimed on an open socket; one more gets `voters_full`) × at most `VOTE_BUDGET_MAX` (20) rows each (every row holds at least one dot) = **800 rows** a round, tens of bytes each (under 100 KB). The cap bounds what a script can do with fresh keys: a 41st voter in a round is refused, and a new round needs the host.
- *Messages:* the largest `votesRevealed` (200 notes, each with 40 × 20 = 800 dots, the largest round number) is **8,460 bytes**, far under `MAX_SERVER_MESSAGE_BYTES` (512 KiB; `shared/test/voting.test.ts` fails past 16 KiB). The largest `voterGranted` (20 notes) is 846 bytes. Client messages: `claimVoter` at most 94 bytes, `voteSet` 57, far under `MAX_MESSAGE_BYTES`.
- *Joining:* `joined` carries `voting` (read from memory); the 8 KiB tripwire for the largest `joined` still holds (tested with the voting state at its widest). A joiner while voting is closed also gets `votesRevealed` right after the snapshots (computed from memory, at most 8,460 bytes); while open, nothing about votes.
- *Burial:* End session and expiry drop the votes table with every other table (tested: only the tombstone survives); the voting meta keys go with meta.

## Live cursors (protocol v14): what pointers cost

Live cursors answer flag 1 above. Relay only: nothing is stored, nothing is scheduled, no heartbeat is added. Numbers checked in `worker/test/cursors.test.ts` and `shared/test/cursors.test.ts`.

- *Request cost:* every inbound `cursor` message is billed like any other WebSocket message, **20:1**. The web sends at most one every 100 ms, so one person moving their pointer non-stop is **10 messages/s ≈ 0.5 DO requests/s** (1,800 an hour). Ten people moving non-stop for an hour: **about 18,000 of the 100,000 daily DO requests** (half the 36,000 flag 1 estimated at 20/s).
- *Sending rules that keep it far lower in practice* (web, part 2): only from md up with a mouse or pen (pointer type, not screen size; phones and touch never send); only after the pointer moved at least 1 board unit since the last send; only while at least one other participant is in the room; nothing while the tab is hidden, or while disconnected or reconnecting; one `cursorLeft` when the pointer leaves the board or the window loses focus; a "Share my cursor" switch turns it off. A pointer at rest sends nothing, so a typical workshop (people reading, typing in notes, talking) is a fraction of the non-stop figure.
- *Relay work:* forwarded at once to the other joined sockets (no coalescing, no timer). **0 rows read or written, 0 storage calls** (tested by wrapping every storage method), no alarm touched. Before joining, or alone in the room, a cursor message is dropped without fan-out.
- *Fan-out size:* a `cursorMoved` is **64 bytes** at its longest (`cursorGone` 45). Outgoing messages are not billed as requests. Worst realistic room: 20 people all moving at 10/s = 200 messages/s in, each fanned out to 19 others = 3,800 messages/s out, about 240 KB/s from the object in total, about 12 KB/s to each page. Inbound: `cursor` at most about 50 bytes, `cursorLeft` 21.
- *Rate limits:* cursor messages spend their own per-socket bucket, `CURSOR_LIMITS` (**15/s, burst 20**), and never a `SOCKET_LIMITS` token, so moving a pointer can't starve edits or chat (tested: a full SOCKET_LIMITS burst still goes through after 40 cursor messages). 15/s is 1.5 times the web's 10/s, so timer jitter or a tab catching up after a stall never drops an honest cursor; 20 covers a short burst. Over budget, a cursor is **dropped silently** (the next one supersedes it). **Only sustained abuse is a violation:** up to 100 drops in 10 s are silent (a page bug or a slow machine catching up for a few seconds), and every drop past that in the window counts as a normal violation (20 in 10 s close the socket, as before). Malformed cursor messages fail validation and spend `SOCKET_LIMITS` like any other bad message.
- *Worst-case script on one socket:* before cursors, about 30 accepted messages/s plus at most ~2/s of violations without being closed ≈ **32 messages/s ≈ 1.6 DO requests/s** (≈ 5,800 an hour). With cursors: 30 (SOCKET_LIMITS) + 15 (CURSOR_LIMITS) + 10 silent drops (100 per 10 s) + ~2 violations ≈ **57 messages/s ≈ 2.8 DO requests/s** (≈ 10,300 an hour, about a tenth of the daily budget per socket-hour). So cursors raise the per-socket ceiling by about 1.2 DO requests/s; a faster sender is closed within seconds (100 silent drops, then 20 violations), and opening a new socket costs a Worker and a DO request as always. The residual risk from slice 1 is unchanged in kind: a script with a valid room link can still spend the daily budget, and the plan then fails closed until 00:00 UTC.
- *Hibernation and duration:* a room whose pointers are moving receives messages, so it stays awake and bills duration (flag 3) for as long as someone moves. Idle rooms still hibernate: nothing is sent without movement, the relay schedules nothing for cursors (tested: no alarm, no pending timer, and nothing arrives on its own afterwards), and the cursor state (bucket, "shown" flag) lives in the socket attachment, so a woken object needs nothing (tested across an eviction).
- *Leaving:* a person whose cursor was showing gets one `cursorGone` before `participant_left` (close, error, rate-limit close); End session sends `cursorGone` for every shown cursor before `sessionEnded`. Expiry only buries a room with nobody connected, so there is nothing to remove.

## Frame multi-select (v0.20.0): what moving several frames costs

Web only: no new message, no stored-schema change. It reuses `frameMove`, `frameResize`, `frameEdit`, `frameDelete`, `noteBatch` and `itemsAdd`, so the per-message costs above apply. What's new is how many go out at once. Checked in `web/test/frameSelectMove.test.ts` and `web/test/frameSelectArrange.test.ts`.

- *Live drag, worst case (30 frames and 200 notes selected):* the page sends at most **2 messages every 100 ms** (`SELECTION_LIVE_MESSAGES`, `SELECTION_MOVE_INTERVAL_MS`): one `noteBatch` of up to 50 loose notes, then frames taking turns (each `frameMove` with the ids it carries). That's **20 messages/s**, under `SOCKET_LIMITS` (30/s refill, burst 40), so the bucket stays full during a drag of any length, and at most **500 entries/s** (only the live batch has entries; live `frameMove`s spend none), under `BATCH_LIMITS` (600/s). Locally everything moves on every pointer move; with many frames, others see each frame move in steps (one update per frame every 1.5 s at 30 frames) until the drop. Cost: 20 messages/s ≈ **1 DO request/s while dragging** (a notes-only group drag is 0.5), nothing stored.
- *Drop:* one final `frameMove` per frame (with its carried ids, at most 50) plus the loose notes in final batches of 50: at most **30 + 4 = 34 messages in one burst**, inside the burst of 40 (the bucket is full after any drag, see above). Entries: every carried id and loose note at most once, so **at most 200** (burst 1,000). Rows: 1 per changed frame and 1 per changed note, at most 230.
- *Arrange on frames:* one final `frameMove` (moves, with carried ids) or `frameResize` (Match size) per changed frame, at most **30 messages at once**, at most 200 carried entries. Undo of a move or an arrange sends the same number (frames alone plus note batches), at most 34.
- *Colour or title style for several frames:* one `frameEdit` per changed frame, **paced at 20/s** (`CLEAR_FRAME_STEP_MS`), so 30 frames take 1.5 s.
- *Delete of a selection with frames:* exactly as Clear board: up to 4 note batches at once, then one `frameDelete` every 50 ms.
- *Duplicate of a mixed selection:* one `itemsAdd` per 50 items or 4 KiB, paced like any other add (`ITEMS_STEP_MS`); refused up front past 30 frames or 200 notes, so nothing is sent for it.

## Text and shapes (protocol v15, stored schema 9): what shapes cost

One new object, the shape (text label, rectangle, oval, diamond), in its own `shapes` table. Numbers checked in `shared/test/shapes.test.ts` and `worker/test/shapes.test.ts`.

- *Caps:* `MAX_SHAPES_PER_ROOM` = **50** shapes a room, `MAX_SHAPE_TEXT` = **500** characters each (code points, cleaned like note text). 50 held: the worst case below stays under its tripwire, so it wasn't lowered.
- *Storage:* one row per shape: 21 short columns plus the text (at most 500 characters, up to 2 KB as UTF-8), so under **2.2 KB a row** and about **110 KB** for a full set. A room's notes, frames, votes and shapes stay well under 1 MB. Burial (expiry and End session) drops the table with the others (tested: only the tombstone survives).
- *Join and reconnect: three messages.* `snapshot` (notes) and `framesSnapshot` are unchanged; `shapesSnapshot` follows in the same handler step. Its worst case is **167,686 bytes (163.8 KiB)**: 50 shapes at the largest size, 500 lone-surrogate characters each (6 bytes escaped), the longest keys, z at its lowest and `rev` at `Number.MAX_SAFE_INTEGER`. The test cap is **192 KiB** (196,608 bytes) and it fails past 90% of that (176,947 bytes), the frames rule: a new per-shape field needs a decision first. Why 192 KiB is fine: it's a separate message, about a third of the 512 KiB server cap, leaving well over the 100 KiB headroom the notes snapshot keeps; the notes snapshot's 400 KiB tripwire is untouched.
- *Combined reconnect payload:* **590,221 bytes (576.4 KiB)** on a full board with every frame and shape at its largest (404,229 + 18,306 + 167,686), in three messages, each under the 512 KiB cap. Outgoing messages aren't billed. A realistic board is a small fraction of that.
- *Writes:* adding a shape is **2 rows** (the row and its index entry), like a note. An edit that changes something (text and any style fields together), a final move or resize that changes it: **1 row**; unchanged ones write nothing (tested). A delete is 1 row (measured, in a batch). Live moves and resizes (single or `shapeBatch`) write nothing (tested). A final `shapeBatch` is one transaction, 1 row per changed or deleted shape.
- *Stacking:* notes and shapes share one z space. `notesOrder` may name shapes: only items whose z changes are written (1 row each, one transaction, tested). A `notesOrdered` may now report every note and shape (250 results, about **15 KB** at the widest), when a renumbering at the bound touches the whole space (as rare as before).
- *Frames carrying shapes:* a final `frameMove` carries notes and shapes by one clamped delta, **1 + N + M rows** at most, one transaction (tested). The carry cap of 50 is shared by notes and shapes, so a frame message still names at most 50 items (about 1 KB); the largest `frameMoved` with 50 carried items is under 4 KB (tested).
- *Emoji picker (web only):* it inserts single code points, each one character against the caps (280, 500, 60) and 4 bytes as UTF-8 (JSON sends them unescaped). Lone surrogates (6 bytes escaped) stay the worst case, so every figure above is unchanged; the picker sends nothing of its own (text is saved as before).
- *Entries budget (`BATCH_LIMITS`, 600 a second, burst 1,000):* each `shapeBatch` op, each carried note or shape on a final `frameMove`, each restacked id and each added shape spends one entry, as for notes. Over budget: `rate_limited` naming the shapes (and frame) so the sender rolls back, plus a violation (tested).
- *Requests:* shape messages are ordinary messages under `SOCKET_LIMITS` (30 a second, burst 40), like note messages.
- *Message caps:* `MAX_MESSAGE_BYTES` stays at **4 KiB**. Every single valid shape fits a message on its own: the largest `shapeEdit` and a one-shape `itemsAdd` with 500 lone surrogates, 500 four-byte emoji or 500 control characters (all tested). Shapes per `itemsAdd`: **1** at its largest, **14** with short content (empty text, 12-character refs).
- *Moving a selection with shapes (web, part 3):* notes and shapes selected together, or with frames, move as one selection drag. The page still sends at most **2 messages every 100 ms** (20 a second, under `SOCKET_LIMITS`), and at most **one live batch per tick** (a note batch and a shape batch take turns when both are selected), so live entries stay at most **50 per tick, 500 a second**, under `BATCH_LIMITS` (600). Frames take the other slot in turn, each `frameMove` with the notes and shapes it carries (no entries spent while live). With notes and shapes but no frames, each kind's live update reaches others every 200 ms; locally everything moves on every pointer move. Cost: about **1 DO request a second while dragging**, nothing stored.
- *Dropping it:* one final `frameMove` per frame (its carried notes and shapes, at most 50 together), the loose notes in final batches of 50 and the loose shapes in one final `shapeBatch` (at most 50): at most **30 + 4 + 1 = 35 messages** in one burst, inside the burst of 40. Entries: every carried or loose item once, at most **250** (200 notes and 50 shapes), inside the burst of 1,000. Rows: 1 per changed item.
- *Deleting a mix or clearing the board:* notes in batches of 50 and shapes in one `shapeBatch` at once (at most 5 messages, 250 entries), then frames paced as before. One undo adds everything back through `itemsAdd` (notes and shapes ranked so their stacking is kept).

## Follow and Bring to me (protocol v19): what following costs

Relay only, like cursors: nothing is stored, nothing is scheduled, no heartbeat. Numbers checked in `worker/test/follow.test.ts`, `shared/test/follow.test.ts` and `web/test/follow.test.ts`; measured on 9 October 2026 (v0.30.0, part 1). Since v0.31.0 (the UI) pages really send these: the canvas offers every view change and the same throttle applies, so the numbers below are unchanged; the UI adds no message of its own, and Bring to me's button is off for 5 s after each send, so a page never spends the relay's burst.

- *Request cost:* every inbound `viewport` is billed like any other WebSocket message, **20:1**. The web sends at most one every 200 ms (5 a second), only while `followersChanged.count > 0`, only when the view moved at least 1 board unit or the zoom by 0.001, never from a phone and never from a hidden tab. Measured: a one-minute continuous pan at 60 frames a second sends **287 viewport messages (about 4.8 a second)**, so one followed person panning non-stop is **about 0.24 DO requests/s** (about 860 an hour). A person nobody follows sends nothing. A person at rest sends nothing.
- *Worst case with the cap:* the follower cap (`MAX_FOLLOWERS` 10) bounds fan-out, not requests: inbound is one message per leader whatever the number of followers. The most leaders a full room (20) can have at once is 20 (a ring, each following the next), all panning non-stop: 20 x 5 = **100 messages/s ≈ 5 DO requests/s** (18,000 an hour, about a sixth of the 100,000 daily requests), still half the cursor worst case (20 x 10 a second). Realistic: one facilitator followed by the room, panning a third of the time: about 0.08 DO requests/s, under 300 an hour.
- *Fan-out size:* a `viewportUpdate` is **80 bytes** at its longest; `followersChanged` 38, `followEnded` 45, `broughtToMe` 79. Inbound `viewport` is at most about 76 bytes as the web sends it (whole units and 3 decimals of zoom). Outgoing messages aren't billed as requests. Worst single leader: 10 followers x 5 a second = 50 messages/s out, about 4 KB/s from the object.
- *Follow, unfollow and counts:* `followStart` / `followStop` spend `SOCKET_LIMITS` like chat; each answers with at most one `followersChanged` to one or two people (old and new target) or one `followEnded` to the sender. A leave sends one `followersChanged` to the person it followed and one `followEnded` to each of its followers (at most 10), before `participant_left`.
- *Bring to me:* host only, its own bucket `BRING_LIMITS` (**1 every 5 s, burst 2**), so at most about 0.2 inbound messages a second ≈ 0.01 DO requests/s; each fans out once to everyone else (at most 19 x 79 bytes). Not stored, nothing kept for late joiners.
- *Rate limits:* viewports spend their own per-socket bucket, `VIEWPORT_LIMITS` (**10/s, burst 10**), twice the web's rate, never a `SOCKET_LIMITS` or `CURSOR_LIMITS` token (tested: a whole SOCKET_LIMITS burst of chat still goes through after a viewport flood). Over budget a viewport is dropped and counted as a violation with no reply; 20 violations in 10 s close the socket (tested).
- *Worst-case script on one socket:* the v14 ceiling (about 57 messages/s ≈ 2.8 DO requests/s) plus 10 viewports/s and 0.2 bring/s, with no extra silent drops (every over-budget viewport is a violation, which share the ~2/s allowance): **about 67 messages/s ≈ 3.4 DO requests/s** (about 12,100 an hour). The residual risk is unchanged in kind.
- *Relay work:* forwarding reads the open sockets' attachments (at most 20) to find followers; **0 rows read or written, 0 storage calls** with or without followers (tested by wrapping every storage method), no alarm or timer. With no followers a viewport has **zero fan-out**.
- *Hibernation and duration:* a followed person who is panning keeps the room awake (flag 3), as cursors do; idle rooms still hibernate. Who follows whom lives in each follower's socket attachment (`following`, a 16-character id), so a woken object rebuilds counts from attachments, never storage (tested across three evictions).

## Silent brainstorm (protocol v17, stored schema 10): what sealed notes cost

Part 1 (relay and shared). Numbers measured in `worker/test/silent.test.ts` and `shared/test/silent.test.ts`.

- *Requests:* `silentStart` and `silentReveal` are one inbound message each (22 and 23 bytes), billed 20:1 like any other: **1/20 of a DO request per host message**. A sealed add, edit, move or delete is the same message as before. `join` with a key is the same one message (about 40 bytes more); the writer id is one HMAC in the object (CPU only, no storage call).
- *Rows written:* `silentStart` **4 rows** the first time in a room (two new meta keys, each a row and its index entry), **2** after that (both keys rewritten); a second start while one runs, or a reveal with none running, writes **0**. A sealed add is **2 rows**, exactly as a note (the row and its primary-key index; `sealed` and `writer` are not indexed); a sealed note's edit, final move or resize **1**, a delete as before. Count broadcasts write nothing. `silentReveal` is **one transaction: 1 row per sealed note plus 1 for the flag**, so at most **201 rows** (200 sealed notes; measured), and its `UPDATE` reads at most the room's 200 note rows.
- *Storage:* a sealed note's row is 2 bytes plus a 43-character writer id bigger (under 50 bytes a note, under 10 KB for a full room), and the id is dropped at the reveal. Two meta keys. The socket attachment gains the writer id: the largest attachment is about 620 bytes, far under the 16 KiB limit (the test caps it at 1 KiB).
- *Outgoing (not billed as requests):* every sealed add or delete sends one `silentChanged` to everyone, **50 bytes** at its longest (`count` 200): about 1 KB per change in a room of 20. Edits and moves of a sealed note go only to its writer's sockets, so a silent round sends less than a normal one. The reveal sends every sealed note to everyone in `notesRevealed` chunks of 50: the largest chunk is **101,098 bytes** (50 notes at their largest, lone-surrogate text, maxed revs; the test fails at 128 KiB), so a full board is 4 chunks, about **404 KB per person and about 8.1 MB for 20 people**, once, bandwidth only (no rows, no requests). A writer's own notes come again in it (same id and rev).
- *Filtering:* while any note is sealed, every note-carrying message is filtered per recipient and encoded once per distinct writer (at most 20 encodings for 20 people, in memory, no storage calls). With no sealed note the filter is skipped and broadcasts encode once, as before.
- *Caps:* `MAX_SEALED_PER_WRITER` 40 sealed notes per writer (a page's key), inside the 200-note room cap; `notesRevealed` at most 50 notes a message; nothing else new. Rate limits unchanged: the silent messages spend `SOCKET_LIMITS` like any other.
- *Hibernation:* nothing is scheduled; the round is in meta, the seals in the notes table and each socket's writer in its attachment, so a woken object needs nothing else (tested across an eviction).
- *Burial:* End session and expiry drop sealed notes, their writer ids and the round's meta keys with everything else (tested: only the tombstone survives).
- *UI (v0.28.0, web only):* no relay cost: the strip, marker, counts and host buttons use the messages above (one `silentStart` or `silentReveal` per confirmed press).
- *Web state (v0.27.0, web only):* no new message and no new row. `join` now always carries the key (about 40 bytes more, as above); the page refuses up front what the relay would refuse during a round, so it sends fewer refused messages, never more.
- *Which notes are mine (protocol v18):* one `silentMine` per join during a round, to the joining socket only, at most **789 bytes** (40 ids); 0 rows, no storage call beyond the notes already in memory, nothing on adds or deletes.

## Reactions on notes (protocol v20, stored schema 11): what reactions cost

Part 1 (relay and shared). Row counts measured in `worker/test/reactions.test.ts` (`rowsWritten`) on 13 October 2026 (v0.33.0); message sizes from the shared schemas (`shared/test/reactions.test.ts` checks the largest).

- *Rows written per reaction:* turning a reaction on is **2 rows** (the row and its primary-key index entry, like a new vote); turning it off is **1 row** (a delete); setting it to what it already is writes **0** and sends nothing. A note's delete (single, batch, Clear board) also runs `DELETE FROM reactions WHERE note_id = ?` in the same transaction: **+1 row per reaction on that note** (0 when it has none). End session and idle expiry drop the table with every other one (dropping a table isn't counted as row writes), so the burial costs are unchanged.
- *A busy 10-person session:* a one-hour retro with about 60 notes where each person puts about 45 reactions on and takes about 5 off: 10 x (45 x 2 + 5 x 1) = **950 rows**. If the host then clears the board with about 400 reactions still on its notes: **+400 rows**. About **1,350 rows**, roughly **1.4%** of the 100,000 rows written a day; the same session with the board left to expire, or ended, is about 950 rows (under 1%). Reactions alone, about **70 such sessions a day** would reach the daily limit.
- *Requests:* each `reactionSet` is one inbound message (79 bytes at its longest), billed 20:1: the session above (500 messages) is **about 25 DO requests**. Joining is the same one request as before.
- *Caps:* `MAX_REACTIONS_PER_ROOM` **2,000 rows** a room (beyond: `reactions_full`), `MAX_REACTIONS_PER_REACTOR` **100** per reactor (beyond: `reactor_full`), so a full room of 20 at their own cap just fits. Proposed from this file: the room cap keeps a room's reactions under about 160 KB (a row is a 43-character reactor id, a 16-character note id and a key, under 80 bytes) and its largest snapshot under 70 KB; filling a room from empty is at most **4,000 rows**, and deleting everything with the notes at most 2,000 more. Turning a reaction off always works at a cap. Rows the relay didn't write (left by older code on a note it deleted, or with a key outside the six) are skipped on load and don't count.
- *Rate:* reactions spend their own per-socket bucket, `REACTION_LIMITS` (**4/s, burst 12**), never a `SOCKET_LIMITS` token (tested: a reaction leaves the message bucket full, and edits still go through with the reaction bucket empty). Over budget: `rate_limited` naming the note, counted as a violation (20 in 10 s close the socket). Worst case for one script on one socket: 4 a second alternating on and off is about **6 rows/s, about 21,600 rows an hour**, which would use the daily rows in under 5 hours. That is the same kind of risk as the existing edits (a `noteEdit` at 30/s writes 1 row each) and smaller; it is measured and left as is by the hardening pass (v0.39.1, "Hardening findings" below).
- *Outgoing (not billed as requests):* each change sends one `reactionCount` (**83 bytes** at its longest) to everyone who may see the note and one `reactionMine` (**80 bytes**) to the reactor's own sockets: about 1.7 KB per change in a room of 20. The join step's `reactionsSnapshot` is **70,439 bytes** at its theoretical largest (every note, every key, room-cap counts) and about 67 KB at the real cap (2,000 rows over 1,200 note-key pairs); empty it is 41 bytes. The largest `voterGranted` (20 votes and 100 reactions) is **5,681 bytes**.
- *Reads and memory:* the reactions are read once when the object wakes (at most 2,000 rows plus any skipped ones) and kept in memory by note and key, so counts, caps and snapshots read no rows.
- *Hibernation:* nothing is scheduled; the reactions are in the table and each socket's reactor is its voter id in the attachment (unchanged). The attachment gains two numbers (the reaction bucket).
- *The UI (v0.34.0, web only):* no new message and no new row. The page already claimed a voter on every join (since v0.17.0), so joining costs the same; a press sends one `reactionSet` only when it changes my state (the page never sends a set it already shows, so no "same again" messages), and refusals it can see coming (offline, no voter, sealed or unsaved note) send nothing.
- *Silent rounds:* a reaction on a sealed note is refused for everyone (its writer too), and sealed notes are left out of every count at the source, so a round adds no filtering work beyond the existing per-recipient filter (the three reaction messages pass through it as a backstop).

## Connectors (protocol v21, stored schema 12): what arrows cost

Part 2 (v0.36.0, web only) adds no message: the page sends connector messages through its own bucket (`web/src/connectors/pace.ts`, burst 96, 3.5 a second, inside `CONNECTOR_LIMITS`), so Clear board with 100 arrows sends 96 deletes at once and the rest within about 1.2 s, before any item delete (so no row is spent freeing an end of an arrow that's going). Moving items with attached arrows still sends and writes nothing for the arrows.

Part 1 (relay and shared, arrows part 1 of 2). Row counts measured in `worker/test/connectors.test.ts` (`rowsWritten`) on 14 October 2026 (v0.35.0); message sizes from the shared schemas (`shared/test/connectors.test.ts` checks the largest).

- *Rows written:* adding a connector is **2 rows** (the row and its primary-key index entry, like a shape); an update that changes something (any ends and style fields together) **1 row**; an unchanged update **0** and sends nothing; a delete **1 row**. The delete rule: a note or shape delete (single, batch, Clear board's batches) writes **+1 row per connector bound to it**, in the same transaction (0 when none). Moving or resizing a bound item writes **nothing extra** (a bound end stores no coordinates; tested: a final move and a final resize of a note with two connectors cost exactly what they cost without). End session and idle expiry drop the table (not counted as row writes).
- *A busy session:* 40 arrows drawn, each restyled or re-attached twice, 10 deleted: 40 x 2 + 80 x 1 + 10 x 1 = **170 rows**; clearing a board with 30 arrows on it: up to 30 detach rows plus 30 deletes (part 2's Clear board deletes them) = **60 rows**. Well under 1% of the 100,000 rows written a day.
- *Requests:* each connector message is one inbound message (the largest `connectorAdd` is 282 bytes), billed 20:1: the session above (about 130 messages) is **about 7 DO requests**.
- *Cap:* `MAX_CONNECTORS_PER_ROOM` **100** a room (beyond: `connectors_full`). Chosen from this file: a row is 17 short columns (two 16-character ids at most, short keys), under 200 bytes, so a full set is under 20 KB of storage; filling a room from empty is at most **200 rows**, and its largest snapshot is about 29 KB.
- *Join and reconnect:* one more message in the join step, `connectorsSnapshot`. Worst case **29,144 bytes**: 100 connectors with both ends bound (16-character ids, the longest anchor "bottom"), the longest key of every style field, `rev` at `Number.MAX_SAFE_INTEGER`; free ends are shorter (the same 100 free-to-free: 23,944 bytes). The test cap is **36 KiB** (36,864 bytes) and it fails past 90% of that (33,178 bytes): a new per-connector field needs a decision first. Empty, it is 45 bytes. It's a separate message, far under the 512 KiB server cap; the combined reconnect payload grows by at most that much.
- *Outgoing (not billed as requests):* each add sends one `connectorAdded` (375 bytes at its longest, with the sender's `clientRef`), each update or detach one `connectorUpdated` (330 bytes at its longest) to everyone in the room: about 6.6 KB per change in a room of 20.
- *Rate:* connector messages spend their own per-socket bucket, `CONNECTOR_LIMITS` (**4/s, burst 100**), never a `SOCKET_LIMITS` token (tested). The burst is a whole room's worth, so part 2 can delete every connector at once on Clear board, or add a duplicated selection's arrows in one go; 4 a second is faster than anyone draws. Over budget: `rate_limited` naming the `clientRef` or connector, counted as a violation (20 in 10 s close the socket). Worst case for one script on one socket: 100 messages at once, then 4 a second alternating add and delete is about **6 rows/s, about 21,600 rows an hour**: the same order as reactions and smaller than the existing edits (a `noteEdit` at 30/s writes 1 row each); measured and left as is by the hardening pass (v0.39.1, "Hardening findings" below).
- *Reads and memory:* connectors are read once when the object wakes (at most 100 rows plus any skipped ones) and kept in memory, so caps, binds, detaches and snapshots read no rows.
- *Hibernation:* nothing is scheduled; the attachment gains two numbers (the connector bucket).
- *Silent rounds:* every connector message is refused during a round (`silent_active`), so a round adds no work; a detach during a round only names the visible note or shape being deleted. The three note-carrying connector messages pass through the existing per-recipient filter as a backstop.

## Groups (protocol v22, stored schema 13): what groups cost

Structure part 1 of 3 (relay and shared). Row counts measured in `worker/test/groups.test.ts` (`rowsWritten`) on 14 October 2026 (v0.37.0); message sizes from the shared schemas (`shared/test/groups.test.ts` checks the largest).

- *Storage:* `groups` is one short row per group (a 16-character id, a label of at most 40 characters, a colour key, rev), under 200 bytes; `group_members` is `WITHOUT ROWID` (no separate key index), one row per member of two 16-character ids. A full room (30 groups, all 250 notes and shapes grouped) is under 20 KB. No box is stored, so moving or resizing a member writes nothing for groups (tested).
- *Rows written (one transaction each):* `groupCreate` **2 + 1 per member** (the group row and its key index, then one row per member, whether new or moved from another group); `groupUpdate` **1**, unchanged **0** and nothing sent; `groupMembers` **1 per id that changes** (added, moved in or taken out) **+ 1** for the group's rev; `groupDelete` **1 + 1 per member**. Every other group a move touches costs **+1** (its rev) if it keeps 2 or more, or **1 + 1 per member left** if it is dissolved. A dissolve is always the group row plus one row per member left.
- *Deletes:* a note or shape delete (single, batch, Clear board's batches) writes, on top of its usual rows, **+1 per grouped item deleted**, **+1 per group it shrinks** (still 2 or more) and **1 + members left per group it dissolves** (tested on a two-note batch: plain + 2 + 1 + 2). A batch delete of N grouped notes that empties G groups is about **plain + N + 2G**. Clear board with every note and shape grouped (250 items, 30 groups): ungrouping first costs 30 x (1 + members) = **280 rows**; leaving it to the relay costs the same 280 plus one rev row each time a batch only shrinks a group that a later batch dissolves (notes go in up to 4 batches of 50, then shapes: at most about 150 more). Ungrouping first saves those rows and the messages that go with them.
- *Largest single message:* a `groupCreate` of 100 members, each taken from a group it leaves with one member: 2 + 100 + 29 x 2 = **160 rows**. `groupDelete` at most **101**.
- *A busy session:* 15 groups of 8 made, each renamed and recoloured twice and changed twice by 2 items, 5 ungrouped: 15 x 10 + 30 x 1 + 30 x 3 + 5 x 9 = **315 rows**, well under 1% of the 100,000 rows written a day.
- *Requests:* each group message is one inbound message (the largest `groupCreate` 2,250 bytes, the largest `groupMembers`, 100 to add and 100 to take out, 3,866 bytes, both under `MAX_MESSAGE_BYTES` 4 KiB), billed 20:1 like any other.
- *Join and reconnect:* one more message in the join step, `groupsSnapshot`. Worst case **14,686 bytes**: 30 groups holding all 250 notes and shapes, 40 lone surrogates in every label (6 bytes each escaped), the longest colour key, `rev` at `Number.MAX_SAFE_INTEGER`. Stored labels can't hold lone surrogates (SQLite keeps UTF-8), so a real full room is smaller (40 four-byte emoji: 12,286 bytes). The test cap is **20 KiB** (20,480 bytes) and it fails past 90% (18,432): a new per-group field needs a decision first. Empty, it is 37 bytes. The combined reconnect payload grows by at most that much; every message stays far under the 512 KiB server cap.
- *Outgoing (not billed as requests):* `groupCreated` at most 2,308 bytes, `groupUpdated` 2,261 (100 members, the longest label), `groupDeleted` 47, to everyone in the room.
- *Rate:* group messages spend their own per-socket buckets, `GROUP_LIMITS`, never a `SOCKET_LIMITS` token (tested): **2 messages a second, burst 60** (every group ungrouped and re-added at once, before a Clear board and its undo), and **10 member ids a second, burst 250** (every note and shape on a full board). Over either: `rate_limited` naming the `clientRef` or group, a violation (20 in 10 s close the socket), and nothing spent. Worst case for one script on one socket: member ids at 10 a second write about 10 rows a second, their later removal or dissolve about as many again, plus the group rows of 2 messages a second: about **25 rows a second, about 90,000 an hour**, the same order as a `noteEdit` script at 30 a second; measured and left as is by the hardening pass (v0.39.1, "Hardening findings" below).
- *The page (v0.38.0):* every group message goes through a client pacer a little inside both buckets (56 messages then 1.75 a second; 240 member ids then 9 a second), so Clear board's 30 ungroups and its undo's 30 re-creates go at once and a page never earns `rate_limited` from its own groups (tested by replaying the sends through the relay's buckets). Moving a group is item batch moves only: no group message during or after a drag.
- *Reads and memory:* groups are read once when the object wakes (at most 30 group rows and 250 member rows, plus any left by a rollback) and kept in memory.
- *Hibernation:* nothing is scheduled; the attachment gains four numbers (the two group buckets).
- *Silent rounds:* every group message is refused during a round (`silent_active`), so a round adds no work; a member's delete during a round only names visible items. The three member-carrying group messages pass through the per-recipient filter as a backstop.

## Stencils (v0.39.0): what placing one costs

Web only; nothing new on the relay. Saved stencils live in this browser (at most 20, 24 KB each, 200 KB in all) and cost nothing until placed.

- *Placing one* is the same messages as adding the items by hand: itemsAdd messages of up to 50 items (paced at 10 a second), then one `connectorAdd` per arrow and one `groupCreate` per group (paced inside `CONNECTOR_LIMITS` and `GROUP_LIMITS`). The largest built-in (Pros and cons) is 7 items and 2 groups: 1 itemsAdd and 2 groupCreates. A saved stencil can be at most the room's caps, so its worst case is a full board's worth of adds, which the room refuses up front when it wouldn't fit.
- *Rows written* are those of the add messages (LIMITS.md "Create with content", "Connectors", "Groups").

## Export on phones and Import (v0.40.0): what they cost

Web only; nothing new on the relay, no new message type.

- *Export* on phones (the share sheet) and *Export board file* are made in the browser like the other exports: no message, request or row. Zero relay cost.
- *Import file cap*: **1 MB** (UTF-8 bytes; `IMPORT_MAX_BYTES`, for a board file and for text alike), checked on the file's size before it is read and on the text before it is parsed. The largest board Stickyard can hold (200 notes of 280 four-byte emoji, 50 shapes of 500, 30 frames, 100 arrows, 30 groups) exports to about 470 KB (tested), so the cap leaves about twice that.
- *Placing an import* is the same messages as placing a stencil (above): itemsAdd messages packed by size (up to 50 items, paced at 10 a second), then one `connectorAdd` per arrow and one `groupCreate` per group (paced inside `CONNECTOR_LIMITS` and `GROUP_LIMITS`). A full board's import from empty is 280 items: from about 20 itemsAdd messages (short text) to about 150 (every item at its longest text; a message is at most 4 KB), paced at 10 a second so under 15 seconds, then 100 connectorAdds and 30 groupCreates: the same as building that board by hand, or as Clear board's undo of it. An import that wouldn't fit is refused in the browser before anything is sent.
- *Rows written* are those of the add messages (LIMITS.md "Create with content", "Connectors", "Groups").

## Frame membership (protocol v23, stored schema 14): what `placed` costs

Every note, shape and frame carries `placed`, the room's placement counter (one value per message that adds items or moves them to a new place; a frame and what it carries share one). Decided 15 October 2026, with the fix it serves: a frame carries only what was placed at or after it.

- *Rows written:* none extra. The value is written in the same row write as the add or the final move that sets it (an `UPDATE` that already happens). A carried item that somehow didn't move (never seen; the delta is clamped for the group) takes the frame's value as a stored change: 1 row, as a move. Live moves, resizes, edits and restacks don't touch it. The counter itself is never stored: it is read once, as the highest stored value, when the object wakes.
- *Storage:* one integer column on notes, frames and shapes (`placed INTEGER NOT NULL DEFAULT 0`), under 10 bytes a row. Old rows read 0, which the web treats as placed before v23.
- *Messages:* `,"placed":<n>` on every note, shape and frame (26 bytes at its widest, `Number.MAX_SAFE_INTEGER`), and on final `noteMoved`, `shapeMoved` and `frameMoved` that changed a place. Worst cases, recomputed in the tests:
  - notes `snapshot` **409,429 bytes** (was 404,229; +5,200): 171 bytes under the 400 KiB tripwire, 114,859 bytes (112.2 KiB) of headroom under the 512 KiB cap, above the 100 KiB rule. The next per-note field still needs that tripwire revisited first.
  - `framesSnapshot` **19,146 bytes** (was 18,366; +780). That is past the old 90% tripwire of the 20 KiB cap (18,432), so the cap is raised to **24 KiB** (24,576; tripwire 22,118). Decided 15 October 2026 with this change: it's a separate message, under 4% of the server cap, and a placement value per frame is what the fix needs. The 10% rule stands for the next per-frame field.
  - `shapesSnapshot` **169,086 bytes** (was 167,786; cap 192 KiB and its 90% tripwire unchanged). Combined reconnect worst case (notes, frames, shapes) **597,661 bytes** (was 590,381), still three messages each under the cap.
  - The largest `notesRevealed` chunk **102,398 bytes** (was 101,098; under 128 KiB), the largest `itemsAdded` **104,953 bytes** (was 103,653). `frameMoved` with 50 carried items stays under 4 KiB (one `placed` per message, not per item).
- *Silent rounds:* adds and moves of sealed notes alone take the current value without advancing it, so the values everyone else sees have no gaps that would hint at hidden activity.
- *Client messages:* unchanged. No client message carries `placed` (the item schemas are strict), so nothing new is accepted from a page.

## Hardening findings (v0.39.1)

The basic hardening pass, measured on 14 October 2026 against a local `wrangler dev` only (fake secrets, a fake room-signing key, throwaway storage; never the deployed Worker). Rerun with `npm run load` (correctness, below) and the worker test `worker/test/budget.test.ts` (rows). The machine was a shared cloud container, with the clients and `wrangler dev` on the same CPU: **message counts, rows and correctness are reliable; every time below is rough**.

**What a local run cannot show.** Cloudflare's real CPU limit per request and its 128 MB memory limit (workerd locally has neither), how duration is billed for an object that is awake between messages, hibernation and eviction timing, network latency between people and the relay, the real behaviour of a deploy (locally a stopped `wrangler dev` left new connections hanging until the page's 10 s join timeout instead of refusing them), and what the account dashboard bills. Those need a real session with friends (see the hand-check list in the PR).

**Correctness under concurrency** (12 simulated pages: the web's own `RoomSession` over Node WebSockets, every frame recorded per recipient):
- *Burst of edits:* 12 pages each making 40 to 80 random gestures (add, edit, style, drag, resize, delete notes; group drags; z-order; frames added, renamed, dragged with notes, deleted; shapes; arrows added, re-attached, deleted; groups created, renamed, changed, ungrouped; reactions), about 1,000 to 2,100 messages in 6 to 12 s, several seeds. After the room went quiet every page's board was compared, item by item, with a fresh join's snapshot. **Two web defects found and fixed** (below); after the fixes, 0 differences on every seed, and no honest page earned `rate_limited` or any other error.
- *Silent round:* 6 writers (one with a second tab on the same key) added 22 sealed notes, edited, moved and deleted some, while others kept working; a guessing socket sent edits, moves, deletes, reactions, an arrow, a group and a restack at sealed ids. Every frame each recipient got during the round (482) was checked: **no sealed id or text reached anyone but its writer's tabs** (ids a socket sent itself and gets back in an error are not counted, exactly as for an unknown id). Counts were honest on every page (21 after a delete), the second tab saw the same sealed notes, the guesser got only `unknown_note` and `silent_active` and changed nothing, and after the reveal every page matched the relay.
- *Follow and Bring to me:* 10 followers (the cap; an 11th got `followers_full`), the leader's 20 offered views became 6 `viewport` messages (the 5-a-second throttle), each delivered to every follower and to nobody else; a leader drop told every follower `target_left` (followers do not re-follow the leader's new id); Bring to me reached everyone but the host once; the host leaving told only its followers.
- *Dot voting:* 13 voters at once, a budget of 3; two tabs with one key spending the budget at the same moment got one `voteConfirmed` and one `over_budget`; nothing about anyone else's votes reached anyone while open; the totals equalled every vote placed, every page showed the same results, and a late joiner got them.
- *Locked board:* a raw guest socket sent all 26 board-changing message kinds and got 26 `board_locked`, the relay's board unchanged; reactions still worked; the host's edit went through. (The web session itself doesn't refuse a guest's add on a locked board: the canvas hides the tools; the relay refuses and the page rolls back.)
- *Reconnect storm:* all 12 sockets dropped at once with the relay up: **exactly 1 try per page**, everyone back in about 1.1 s, 0 differences. A "deploy" (relay stopped about 10 s, restarted on the same storage): 1 try per page while down and 2 in all, at least 11.7 s apart (each try waited out the 10 s join timeout locally), no health probes, everyone back about 3 s after the relay was up, 0 differences. With 40 s down: 3 to 4 tries per page. Never a loop.
- *Misbehaving socket:* 12 malformed frames (not JSON, wrong types, a 3,800-deep nested array, a 5,000-character message, out-of-range values, a second join, a wrong host key) each got one reply (`bad_message`, `too_large`, `already_joined`, `bad_host_token`) and nothing broke. Then 4,000 messages flooding every bucket: **closed with 1008 in 1.3 to 3.5 s**, after 14 `rate_limited` replies; what got through before the buckets emptied was 11 chat lines and 12 notes (inside the burst); the 11 honest pages saw no errors, their adds still confirmed in about 1 ms locally, and they matched the relay afterwards.
- *Known gap (backlog):* a drag cut off before its drop (the dragger's connection drops mid-drag) leaves every other page showing the last live preview (measured: 500 units off) until that item changes again. The relay never stored it, so a reload fixes it.

**Full room** (every cap, the longest storable content: 4-byte emoji, as lone surrogates can't be stored): 200 notes of 280 emoji at 480 x 480, 50 shapes of 500 emoji, 30 frames with 60-emoji titles, 100 arrows bound at both ends, 30 groups holding all 250 notes and shapes with 40-emoji labels, 2,000 reactions (20 reactors at their 100). One more of each was refused (`notes_full`, `shapes_full`, `frames_full`, `connectors_full`, `groups_full`, `reactions_full`); nothing was truncated (a fresh join and a web page both showed every item and all 2,000 reactions).
- *Join-step messages:* `joined` 296 bytes, notes `snapshot` **286,159**, `framesSnapshot` 14,067, `shapesSnapshot` 116,466, `reactionsSnapshot` 66,839, `connectorsSnapshot` 27,544, `groupsSnapshot` 11,806: **523,216 bytes (511 KiB) in all**, the largest message at 55% of the 512 KiB cap (the theoretical worst cases above are larger because of lone surrogates).
- *Join time (rough):* 18 to 44 ms for a raw join, 23 ms until a web page shows the board and 39 ms until it shows everything. A reconnect storm of 20 people on such a room is about **10.5 MB** out (not billed as requests).

**Budget: a scripted two-hour session with 12 people.** The session (in `SESSION`, `worker/test/budget.test.ts`): 36 joins (12, then 24 reconnects), a template, 150 notes (40 of them sealed in one silent round), 380 note edits, 400 drags, 40 resizes, 20 group drags, 2 arranges, 20 restacks, 4 frames with 8 renames, 20 carrying moves and 4 resizes, 15 shapes with 30 edits and 20 moves, 30 arrows (20 restyled, 5 deleted), 10 groups (10 renamed, 10 changed, 3 ungrouped), 400 reactions on and 50 off, two voting rounds (5 dots each, 20 changes), 30 deletes, 60 chat lines, 8 timer actions, a lock and unlock, 11 follows and Bring to me. Every stored action was sent for real and counted on the Durable Object (miniflare, the runtime `wrangler dev` uses):
- *Measured:* **2,059 stored or control messages**, **3,235 rows written** (+1 for the expiry alarm at the end), **11,608 rows read** during the session, **490 rows read per wake** at the end of it (every table loaded once). Live drags, cursors, viewports and follows were sampled: 0 rows (tested).
- *Counted from the web's send rates (not stored):* live drag updates **9,400** (400 drags of about a second at 20 a second, and the resizes, group and frame drags), viewports **3,000** (the facilitator followed for 30 minutes, panning a third of it, at 5 a second), cursors **86,400** (8 of 12 on a mouse, moving 15% of the time, at 10 a second; phones send none).
- *Inbound messages:* 14,459 without cursors, **100,859 with**. Cursors are about 86% of a session's messages.

| Free allowance (per day) | One session uses | Sessions a day |
|---|---|---|
| Durable Object requests, 100,000 (36 sockets + messages at 20:1 + 1 alarm) | **5,080** with cursors; 760 without | **19** with cursors; 131 without |
| SQLite rows written, 100,000 | 3,236 | **30** |
| SQLite rows read, 5,000,000 | about 22,000 (11,608 + about 20 wakes of 490) | about 227 |
| Worker requests, 100,000 (36 socket opens + 36 page loads' `/health`) | about 72 | about 1,390 |
| Duration, 13,000 GB-s (128 MB per awake object) | up to 900 if awake the whole two hours | **14** at worst; far more if idle time between messages isn't billed (not measurable locally) |

So: **about 19 such sessions a day** (Durable Object requests, with cursors as assumed), **about 30 with cursors off or rare** (then rows written bind), and possibly **14** if Cloudflare bills the room's whole two hours as awake time. A hobby workshop or two a day is far inside every allowance. Cheapest lever if it ever matters: the desktop cursor rate (10 a second today): 5 a second would roughly double the sessions a day.
- *Scripts inside the limits* (left as is, as noted in the sections above): a script staying under every bucket can still write rows (`noteEdit` at 30 a second, reactions or arrows about 6 rows a second, groups about 25); a flood past them is closed within seconds. The daily hard stop is the cap.

**Fixed in v0.39.1** (tests first): a note, shape or frame dragged on one page while someone else resized it kept the old size on that page for good (dragging now holds only the position); a frame deleted by someone else mid-drag left the notes and shapes it carried held on the dragger's page and showing as its last live preview everywhere else (now they are released and their final positions sent: one notesBatchApplied, the rows of an ordinary drop); muted text on the canvas was 4.44:1 in light (now 4.66:1, `--sy-fg-muted` #566064); the canvas attribution link (15 px tall) and the top bar's start-page link (28 px wide) are full 44 px touch targets. No protocol or stored-schema change.
